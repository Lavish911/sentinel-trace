# Data provenance and isolation

SENTINEL//TRACE uses deterministic synthetic data only. It is not a source of real insurance claims, policyholder information, or production fraud labels.

## Source and generation

`db/seed.py` is the canonical generator for the ARCH-ST-010.3 dataset. `scripts/generate_dataset.py` is its command-line entry point. Given a seed and empty target paths, it builds two SQLite databases:

- `operational.db`: the application-facing 12-table dataset. It contains operational facts, derived indicators, scores, investigations, and the event chain.
- `ground_truth.db`: evaluator-only labels, ring membership, and withheld-edge records used for scenario evaluation.

The seed is an input to reproducibility, not proof that a checked-in database or historical CSV was generated by the current code. Any code change affecting generation requires a fresh run and recorded checksums.

## Isolation boundary

The operational schema does not include fraud labels, scenario codes, ring membership, or withheld edges. API code must use the operational database only. In particular, the `yf_neg_4` scenario filter is deliberately rejected by the operational API because its labels are evaluator-only.

Ground truth is not an authorization source and must not be joined into operational scoring or exposed through the API. The isolation tests verify this boundary when a generated fixture is available.

## Known provenance limits

- Names, addresses, IDs, hashes, and events are synthetic generator output. They are examples, not validated real-world records.
- Historical audit reports, screenshots, checksums, and score CSVs are retained as artifacts. They are not current-run evidence unless regenerated from the reviewed revision.
- The pre-010.3 architecture files are documented as placeholder lineage in `ARCH-ST-010.3.md`; their historical contents are not independently recoverable from this repository.
- Seed data, ground-truth labels, and performance evaluation metrics are exported via `scripts/export_seed_data.py` into `data/` to support offline audit inspection and scenario verification. An operational export pipeline would require field-level access controls, redaction policy, and audit logging before handling production data.

## Scoring alignment note

BC-1 is the high-density-residence benign context. The published architecture specifies a multiplier of `0.35`; the canonical seed and modular scorer use the same value. When multiple benign contexts apply, the generator uses the documented product rule with a `0.15` lower bound. Re-run the negative-case verification after generation rather than relying on values in older export artifacts.
